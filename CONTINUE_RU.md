# Суть задания и что продолжить

## Суть

Нужно написать собственный HTTP/1.1 сервер на Rust, который принимает запросы браузера, выбирает сервер и маршрут по конфигурации, затем отдаёт статические страницы или выполняет действия с файлами. Сервер должен работать в одном процессе и одном потоке, использовать неблокирующий сетевой ввод-вывод и event polling (`epoll` или аналог), выдерживать несколько клиентов и корректно возвращать HTTP-статусы.

В полной версии задания также нужны загрузки файлов, cookies и сессии, настраиваемые страницы ошибок, виртуальные серверы и маршруты, а также запуск хотя бы одного CGI-скрипта. В задании отдельно требуют модульные и стресс-тесты, проверку утечек памяти и сравнение поведения с NGINX.

## Уже сделано

- Создан запускаемый Cargo-проект с конфигурацией-примером, стартовой страницей и страницами ошибок.
- Реализованы HTTP/1.1 запросы GET, POST и DELETE, заголовки, `Content-Length`, `Transfer-Encoding: chunked` и последовательные запросы по keep-alive.
- Есть несколько слушающих адресов/портов, выбор virtual host по `Host`, выбор самого длинного совпавшего маршрута и сервер по умолчанию.
- Работают статические файлы, index-файл, опциональный список каталога, перенаправления, обычные и multipart-загрузки, удаление файлов и проверка выхода за корень сайта.
- Есть лимит тела запроса, тайм-аут клиента, ограничение числа одновременных клиентов, cookie с простым состоянием сессии и страницы ошибок 400/403/404/405/413/500/504.
- Реализован один поток событий: `WSAPoll` на Windows и `epoll` на Linux. CGI подключён: тело передаётся через временный файл в stdin, вывод читается из временного файла, процесс проверяется циклом событий, тайм-аут возвращает 504.
- `hello.py` и `slow.py` находятся в `www/cgi-bin/`; пошаговая памятка Клода добавлена как `NEXT_STEPS_RU.md`. CGI-цикл проверен временным Node-скриптом для GET, POST и 504.
- Добавлено 20 unit-тестов. На Windows проверены сборка, тесты и keep-alive через `curl.exe`.

## Что осталось сделать вручную

1. Перезапустить Windows-конфиг с `py` и проверить `hello.py`, POST-тело, query string и `slow.py` с ответом 504. На ноутбуке `python` указывает на заглушку WindowsApps, но `py -V` показывает Python 3.13.
2. На Linux/компьютере университета запустить `cargo test` и `cargo run -- --config localhost.linux.conf`, проверить ветку epoll и Python CGI.
3. Провести стресс-тест `siege` на собственном `127.0.0.1:8080`, сравнить статусы и заголовки с NGINX и проверить доступность 99.5%.
4. Проверить длительную работу и утечки памяти, в том числе отключение клиента во время CGI.
5. Автоматизировать интеграционные тесты полного CGI-цикла, 504, keep-alive, нескольких запросов в одном TCP-пакете, multipart-загрузки, virtual host и всех страниц ошибок.
6. Если проверяющий ожидает конфигурацию NGINX, адаптировать текущий упрощённый формат из `localhost.conf`.

Сокетные операции неблокирующие, но чтение и запись статических и CGI-временных файлов выполняются синхронно. Это ограничение также отмечено в `README.md`.

## Запуск

Из папки проекта запустите тесты командой `cargo test`. На Windows запускайте `cargo run -- --config localhost.conf`, на Linux — `cargo run -- --config localhost.linux.conf`. Затем откройте `http://127.0.0.1:8080/`.
